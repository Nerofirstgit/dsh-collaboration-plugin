## Packaging

Cordis plugin modules export `name`, `inject`, `Config` (when configurable) and `apply(ctx, config)` or a Service subclass. Contributions use `ctx.on`/`ctx.effect`. Upstream evidence: `docs/cordis-tutorial/01-first-plugin.md`, `docs/architecture.md`, `packages/experimental/agent-team-profile/package.json`. Package `dsh.bundle.patch` points to a `cordis.patch.yml`; install through `dsh plugin`, launch through `dsh --profile … --patch …`. Pin `engines.dsh` and peer packages to the inspected preview version. Direct daemon test fixtures are supporting infrastructure, not a substitute application or claimed host plugin.

## Compatibility result

Lifecycle, context attribution, filesystem provider replacement, tool guards, and a custom canonical SessionPersistence backend are supported plugin seams. No upstream patch is required merely to add those capabilities. Full unmediated-write coverage is a separate security question: unrestricted same-process third-party Host plugins, dynamic plugin management, arbitrary subprocesses, and other profiles must not be claimed protected by tool guards. The protected profile must constrain these capabilities; otherwise protected activation must refuse. This is a capability feasibility finding, not an acceptance-test pass.

The final user scope is **enabled participating sessions only**; disabled plugins and human/manual external processes are outside the guarantee. The implemented constrained path is `src/host/profile.ts` plus the shipped patch: 20 exact audited headless rows, real package identity/version inventory, concrete read-only filesystem/canonical persistence, and readiness injection for both AgentLoop and headless runner. Official root Include topology is established at `packages/boot/app-boot/src/index.ts:770–789`; Loader's real recursive entry inventory is `vendor/loader/src/config/tree.ts:29–35`, and scoped isolation/interception is implemented at `vendor/loader/src/config/isolate.ts:90–161`. No upstream source is modified. Full production boot and two-host-process transport acceptance remain explicitly unverified in this cloud environment.
